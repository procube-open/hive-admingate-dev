# guacd の複数配置と接続記録

`inventory/admingate.yml` は Core Server と guacd から SeaweedFS Filer の
`/recordings` に直接アクセスします。接続記録に共有ボリュームや FUSE は不要です。
`GUAC_RECORDING_PATH` と `GUAC_TYPESCRIPT_PATH` は guacd への接続パラメータであり、
SeaweedFS 選択時の保存先マウントではありません。Selenium 等の別用途の FUSE は変更しません。

## 配備前の条件

- 既存環境では、下記の移行と照合を終えるまで新しい定義を配備しないでください。
  旧記録は自動移行・自動参照されません。
- `latest` は固定されたバージョンではありません。SeaweedFS 記録保存に対応し、
  一緒に検証した Core Server と guacd のイメージを、配備前に固定タグまたは digest で
  指定してください。guacd イメージにはヘルスチェック用の `nc` が必要です。
- guacd は2レプリカ、Swarm VIP、1ノードあたり最大1レプリカです。
  少なくとも2台の利用可能な異なる Swarm ノードが必要で、足りなければタスクは
  pending になります。レプリカ数は定義の `replicas` を手動変更して配備します。
  3以上にする場合も同数以上の配置可能ノードを用意します。
- すべての配置対象ノードの guacd コンテナから、各接続先、Selenium、Filer、
  必要な Socket Warp 経路に到達でき、名前解決できることを確認してください。
  必要なら、準備済みノードを絞る placement constraint を運用者が追加します。
  Core Server から `guacd:4822` と Filer にも到達できる必要があります。
- `HIVE_MARK: guacamole` は hive-builder が guacd の配置ノードに付けるラベルです。
  `idm3-provtools` は引き続きこのラベルに依存します。guacd の配置変更で同サービスの
  配置にも影響し得るため、更新前後に確認してください。

## 旧接続記録の移行と切り替え

AdminGate の
[接続記録の SeaweedFS 移行手順](https://github.com/procube-open/admingate/blob/main/packages/docs-server/docs/operator/recording-migration.md)
に従い、対応するバージョンの `tools/scripts/migrate_recordings.py` を使用します。

1. 旧ボリューム、履歴 DB、Filer／Volume のバックアップと復元方法を確認します。
   旧記録の全配置場所と、切り替え前のサービス定義を記録します。
2. すべての入口で新規ライブ接続を停止し、既存接続と終了処理が完了したことを確認します。
   リースがゼロになっただけでは旧保存先への書き込み停止は証明できません。
   移行中は `/recordings` への全書き込みを停止し、移行ツールを1プロセスだけ実行します。
3. 全旧保存場所の画面録画・タイプスクリプト・再生時刻を移行し、同じ停止状態で
   再実行して内容一致・件数・終了コードを照合します。競合やエラーは解決まで中止します。
   元ファイルは削除せず、旧記録用バックアップも復旧方針が決まるまで保全します。
4. 対応イメージと本定義を配備し、接続を停止したまま移行済み履歴の3種類の取得・再生、
   権限と「状態不明」を確認します。問題がなければ接続を段階的に再開し、新規記録を確認します。
   失敗時は接続を再開せず元データを保全します。切り替え後に作成した SeaweedFS 記録は
   旧保存先に自動コピーされないため、切り戻し時の扱いを事前に決めてください。

新定義は旧 `guacd-recordings` のバックアップ定義を削除します。旧バックアップや DRBD
ボリュームそのものを削除する指示ではありません。自動クリーンアップやボリューム削除を
行う前に、バックアップ保持と移行の完了を別途確認してください。

## 監視と障害・更新

guacd のヘルスチェックはローカルの TCP 4822 のみを確認し、Filer を確認しません。
Swarm の希望／稼働レプリカ数、pending とノード分散、guacd の異常・記録エラーを監視します。
Filer、Master、Volume、PostgreSQL、保存容量、接続記録の不完全・確認不能は別々に監視し、
Filer 障害を理由に全 guacd を再起動しないでください。

VIP は新規 TCP 接続単位で振り分けます。確立済みライブ接続は別レプリカへ移動せず、
guacd 障害、更新、縮小で切断され得ます。利用者は新しいライブ接続として再接続します。
作業時間帯と接続影響を確認して更新・縮小し、配備後にレプリカ配置を再確認してください。

現行 Core Server は guacd 接続前の TCP 試行に `ADMINGATE_CONNECT_TIMEOUT_SECS` を
使用し、この定義では300秒です。短時間再試行は保証されません。この設定は他の接続処理にも
使われるため、単に短縮する前に影響を確認してください。

## バックアップと可用性の限界

既存の hive-backup は SeaweedFS Master、Volume と Filer の PostgreSQL メタデータ、
AdminGate DB をそれぞれ対象にしています。取得時刻が異なるバックアップは自動的に
整合しません。書き込み停止を含む整合した取得・復元手順を準備し、隔離環境で
記録本体と状態・履歴の復元を確認してください。本番データへ試験復元しないでください。

SeaweedFS は `-defaultReplication=000`、PostgreSQL 等もこの定義では単一障害点です。
DRBD や guacd の複数配置だけではシステム全体の高可用性を保証しません。Filer、
Volume、DB の障害時の検知・復旧・切り替えは別途運用設計が必要です。
単一ノードの複数レプリカ試験はノード冗長性の証拠ではありません。異なる実ノードへの
配置とノード停止試験は別途実施し、未実施の間は障害耐性を検証済みとしないでください。
